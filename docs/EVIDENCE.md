# How RPG Maker MZ works — evidence

RPG Maker MZ is not installed on this machine, so the evidence below comes from **MZ's shipped runtime
source**, which every MZ game deploys in `js/`. I read it from a public mirror:

- Repo: `github.com/stak/rmmz-corescript`, commit `5ecc09ae` (2020-10-29)
- Version headers: `rmmz_core.js v1.1.0`, `Utils.RPGMAKER_NAME = "MZ"`, `Utils.RPGMAKER_VERSION = "1.1.0"` (rmmz_core.js:187,195)
- Size: 34,853 lines across `main.js` + six `rmmz_*.js` files + `libs/` (pixi.js, pako, localforage, effekseer, vorbisdecoder)

I also checked these findings against **real MZ project data**: `github.com/restuedos/Project-MZ`
(`game.rmmzproject` = `RPGMZ 1.1.1`, 20 maps, 6 tilesets). See the end of this file.

What the runtime source can't tell you is how MZ's **editor** works internally. It's a closed-source
native app, and I didn't inspect its binary. Every editor behaviour Lakon copies (palette tabs, auto-layering,
right-click quick events, event pages) comes from MZ's documented UI and from the data it writes. It is not
taken from editor code.

---

## 1. Architecture: a native editor that writes JSON, plus a JavaScript runtime

| Layer | Evidence |
|---|---|
| Boot | `main.js` loads, in order: `pixi.js, pako, localforage, effekseer, vorbisdecoder`, then `rmmz_core → managers → objects → scenes → sprites → windows`, then `plugins.js` (main.js:5-18) |
| Rendering | `Graphics._app = new PIXI.Application(...)` (rmmz_core.js:1017). Renders through PixiJS on WebGL |
| Desktop shell | NW.js. The real project's `package.json` has `"main": "index.html"` with `"chromium-args"` and an 816×624 `"window"`, and `index.html` loads `js/main.js`. `StorageManager.isLocalMode` (rmmz_managers.js:541) switches between files and `localforage` for browsers |
| Plugins | `plugins.js` is generated by the editor (`// Generated by RPG Maker. Do not edit`), then `PluginManager.setup` loads each script (rmmz_managers.js:3047,3065) |

The class naming describes the whole design. Each file holds one layer:

- `rmmz_core.js` has the engine primitives: `Bitmap, Sprite, Tilemap, Window, WebAudio, Input, JsonEx`
- `rmmz_managers.js` has the singletons: `DataManager, SceneManager, ImageManager, StorageManager, PluginManager`
- `rmmz_objects.js` has the game state, with no rendering: `Game_Map, Game_Player, Game_Event, Game_Interpreter, Game_Switches…`
- `rmmz_scenes.js`, `rmmz_sprites.js` and `rmmz_windows.js` hold the views: `Scene_Map`, `Sprite_Character`, `Window_Message`

This split, with model in `Game_*` and view in `Sprite_*`/`Window_*`, is the main idea Lakon copies.

## 2. The main loop: a fixed 60 Hz logic tick, decoupled from refresh rate

```js
SceneManager.update = function(deltaTime) {           // rmmz_managers.js:1934
    const n = this.determineRepeatNumber(deltaTime);  // >60 Hz displays run 0 or 1 updates per frame
    for (let i = 0; i < n; i++) this.updateMain();
};
SceneManager.updateMain = function() {                // rmmz_managers.js:2052
    this.updateFrameCount(); this.updateInputData(); this.updateEffekseer();
    this.changeScene(); this.updateScene();
};
Scene_Map.prototype.updateMain = function() {          // rmmz_scenes.js:732
    $gameMap.update(this.isActive()); $gamePlayer.update(this.isPlayerActive()); ...
};
```

Scenes form a stack with `goto` and `push` (rmmz_managers.js:2158-2170). A scene only switches once the
current one isn't busy (`changeScene`, :2075).

## 3. Project data is plain JSON, and arrays are 1-based

```js
  const filename = "Map%1.json".format(mapId.padZero(3)); ...
```

Each database file is an array with `null` at index 0, so IDs start at 1. The real project confirms this:
`MapInfos.json` holds `[null, {"id":1,"name":"Normal Town",...}, ...]`.

## 4. Maps: a flat array of 6 layers

```js
Game_Map.prototype.tileId = function(x, y, z) {        // rmmz_objects.js:6573
    return $dataMap.data[(z * height + y) * width + x] || 0;
};
```

z0–z3 are tile layers. z4 holds shadow bits and z5 holds the region ID. `layeredTiles` reads z3 down to z0 (:6579).

## 5. Tile IDs encode both the sheet and the autotile shape

```js
Tilemap.TILE_ID_B = 0;   TILE_ID_C = 256;  TILE_ID_D = 512;  TILE_ID_E = 768;     // rmmz_core.js:2639
Tilemap.TILE_ID_A5 = 1536; TILE_ID_A1 = 2048; TILE_ID_A2 = 2816; TILE_ID_A3 = 4352; TILE_ID_A4 = 5888;
Tilemap.TILE_ID_MAX = 8192;
Tilemap.getAutotileKind  = id => Math.floor((id - TILE_ID_A1) / 48);   // :2658
Tilemap.getAutotileShape = id => (id - TILE_ID_A1) % 48;               // :2662
```

An autotile "kind" is a block on the A1–A4 sheet. Its "shape" (0–47) indexes `FLOOR_AUTOTILE_TABLE`
(rmmz_core.js:2765). Walls use the 16-entry `WALL_AUTOTILE_TABLE` (:2817) and waterfalls use a 4-entry table (:2837).
Each table entry lists four **quarter-tile** source coordinates. `_addAutotile` (:2472) composites a 48×48 tile
from four 24×24 pieces.

**The runtime never computes shapes.** It only reads them. The **editor** works out each shape from the
neighbouring tiles when you paint and saves it into `data[]`. Lakon has to do the same, which is
`TileID.floorShape` / `refreshAutotile`. A unit test checks that all 256 neighbour combinations map onto the
47 edge shapes in MZ's table.

## 6. Passability: tileset flags, scanned from the top layer down

```js
Game_Map.prototype.checkPassage = function(x, y, bit) {   // rmmz_objects.js:6552
    for (const tile of tiles) {
        const flag = flags[tile];
        if ((flag & 0x10) !== 0) continue;            // [*] No effect on passage
        if ((flag & bit) === 0) return true;           // [o] Passable
        if ((flag & bit) === bit) return false;        // [x] Impassable
    } return false; };
Game_Map.prototype.isPassable = (x, y, d) => this.checkPassage(x, y, (1 << (d / 2 - 1)) & 0x0f);  // :6597
```

Directions use numpad numbering (2 down, 4 left, 6 right, 8 up). A move must pass the exit check on the
source tile and the entry check on the destination (`isMapPassable`, :7075). A ☆ (0x10) tile is drawn above
characters (`_isHigherTile`, rmmz_core.js:2610).

## 7. Characters: tile-locked logic with smooth display

- `distancePerFrame = 2^speed / 256` (:7022). At normal speed 4 that's 1/16 tile per frame, so one step takes 16 frames.
- `animationWait = (9 - speed) * 3` (:7228). Walking adds 1.5 per frame (:7232).
- Sprite sheets: 12×8 frames for eight characters. A `$` prefix marks a single-character sheet and a `!` prefix marks an "object" with no 6 px lift
  (rmmz_managers.js:960-968, rmmz_objects.js:7135). The sheet row is `(direction - 2) / 2` (rmmz_sprites.js:359).
- Draw order uses `screenZ = priorityType * 2 + 1` (:7159), so below = 1, same = 3, above = 5. The upper tile layer sits at 4.

## 8. Events: pages, conditions and triggers

- A page is chosen by scanning from the **last page backwards**. The first one whose conditions all pass wins
  (`findProperPageIndex`, :9286). The conditions are switch 1, switch 2, variable ≥ value, self switch A–D, item and actor (:9297).
- Triggers: 0 Action Button, 1 Player Touch, 2 Event Touch, 3 Autorun, 4 Parallel.
  The action button checks events on the player's own tile first (non-"same" priority), then the tile in front
  (`triggerButtonAction`, :8447; `checkEventTriggerThere`, :8551).
- An event that starts **locks** and turns toward the player. When it finishes it restores its old direction (:9154).
- **Self switches** are keyed by `[mapId, eventId, "A"]` (:9315). This is the standard trick behind "the chest stays opened".

## 9. The interpreter: a flat command list structured by indentation

```js
Game_Interpreter.prototype.executeCommand = function() {  // rmmz_objects.js:9619
    const command = this.currentCommand();
    this._indent = command.indent;
    const methodName = "command" + command.code;            // e.g. command101 = Show Text
    if (typeof this[methodName] === "function") {
        if (!this[methodName](command.parameters)) return false;   // false = block, retry next frame
    }
    this._index++; ...
Game_Interpreter.prototype.skipBranch = function() {       // :9653
    while (this._list[this._index + 1].indent > this._indent) this._index++;
};
```

An event's contents are a flat array of `{code, indent, parameters}`. Blocks such as If/Else/End and choice
branches don't nest. They're shown by `indent` alone, and a false condition skips everything indented
deeper. The source defines 113 `command<N>` handlers. **An unknown code is silently skipped.** Lakon behaves the
same way, which lets imported projects run even where Lakon doesn't implement a command yet.

Examples: `command101` Show Text, which also absorbs the `401` lines that follow it (:9756). `111` Conditional Branch (:9880).
`121`/`122` switches and variables (:10124, :10132). `201` Transfer Player (:10443). `205` Set Movement Route (:10527).
A transfer **does not clear** the running interpreter, so commands after a Transfer Player keep running on the new map.

## 10. Battle maths (ported in `LakonCore/Battler.swift` and `Action.swift`)

```js
Game_BattlerBase.prototype.param = id => Math.round((paramBasePlus * paramRate * paramBuffRate).clamp(min, max)); // :2863
Game_Action.prototype.makeDamageValue = function(target, critical) {    // :1917
    const baseValue = this.evalDamageFormula(target);                     // eval(item.damage.formula) with a, b, v
    let value = baseValue * this.calcElementRate(target);

    if (baseValue < 0) value *= target.rec;      if (critical) value = this.applyCritical(value); // ×3
    value = this.applyVariance(value, item.damage.variance); value = this.applyGuard(value, target); ... };
Game_Actor.prototype.expForLevel = level => Math.round(basis * Math.pow(level - 1, 0.9 + acc_a / 250) * level * (level + 1)
                                            / (6 + Math.pow(level, 2) / 50 / acc_b) + (level - 1) * extra);   // :4141
Game_Action.prototype.speed = () => agi + Math.randomInt(Math.floor(5 + agi / 4)) + item.speed;               // :1637
```

Trait and effect codes are MZ's constants. Examples: `TRAIT_PARAM = 21`, `TRAIT_XPARAM = 22`, `TRAIT_SPARAM = 23`, `EFFECT_RECOVER_HP = 11` and `EFFECT_ADD_STATE = 21`. Imported projects keep their meaning.

## 11. Terrain and vehicle flags (checked against real data)

`isBoatPassable` checks bit `0x200`, `isShipPassable` checks `0x400`, and `isAirshipLandOk` checks `0x800` plus walkability (rmmz_objects.js:6602-6610). Ladder is `0x20`, bush `0x40`, counter `0x80` and damage floor `0x100` (:6619-6631). The real project's world tileset confirms this. Land tiles are `0x600`, so boats and ships can't enter. Deep sea A1 kind 0 is `0x80f` and A1 kind 1 is `0xa0f`, which is ship-only. Vehicle speeds are boat 4, ship 5 and airship 6 (`Game_Vehicle.initMoveSpeed`, :8899).

## 12. Audio and scripts

MZ's `AudioManager` plays Ogg files and reads the `LOOPSTART`/`LOOPLENGTH` Vorbis comments. A real MZ BGM decodes in Lakon with those tags (`Lakon --decode-audio`). Script (`command355`, :11250) is a plain `eval`, and Plugin Command (`command357`, :11273) calls `PluginManager.callCommand`. Lakon reproduces both on JavaScriptCore with an MZ-shaped API.

## 13. Animations: two formats in one file

`Spriteset_Base.isMVAnimation` is just `!!animation.frames` (rmmz_sprites.js:3287), so data/Animations.json can hold both
MZ Effekseer entries and MV cell entries, and MZ 1.1 plays both (`Sprite_Animation`, :1197; `Sprite_AnimationMV`, :1469).

- **MV cells.** Duration is `frames × 4 + 1` with a rate of 4 (`setupRate`/`setupDuration`, :1514-1520). The frame index is
  `frames − ceil(duration / 4)` (:1672), and each cell is `[pattern, x, y, scale, rotation, mirror, opacity, blend]` cut from 192×192
  cells, 5 per row, with pattern ≥ 100 using the second image (`updateCellSprite`, :1692). Timings flash the target, flash the
  screen or hide the target for `flashDuration × 4` frames and play an SE (`processTimingData`, :1724). Position 0 head, 1 centre,
  2 feet, 3 screen (`updatePosition`, :1638).
- **MZ (Effekseer).** The sprite plays `soundTimings` and `flashTimings` per frame and stops once the last timing has passed, the
  flash has ended and the effect handle no longer exists (`updateMain`/`checkEnd`, :1307-1339). It renders with an orthographic
  projection, `y = −1`, `z = −(4096 / height)`, a camera at z = −10 and a 4096×4096 viewport centred on the target (`_render`,
  `setProjectionMatrix`, `setCameraMatrix`, `setViewport`, :1361-1406). The target point is the sprite's centre, or its feet with `alignBottom` (:1425).
- **Scheduling.** Per-target animations start 8 frames in, and each further target 12 frames later (`createAnimation`,
  `animationBaseDelay`, `animationNextDelay`, :3253, :3311-3317). Animations on actors are mirrored (`animationShouldMirror`, :3319).
  The battle waits for them, because `BattleManager.isBusy` (rmmz_managers.js:2391) includes `Spriteset_Battle.isBusy` → `isAnimationPlaying` (rmmz_sprites.js:3696).
- **Which animation.** `Window_BattleLog.showAnimation` treats −1 as a normal attack: actors use their weapon's animation (or 1 for bare
  hands, `Game_Actor.attackAnimationId1`/`bareHandsAnimationId`, rmmz_objects.js:4472-4488), and enemies only play the enemy-attack SE
  (rmmz_windows.js:5534-5575). Show Animation (`command212`, rmmz_objects.js:10553) and Show Battle Animation (`command337`, :11187, whose
  third parameter means the whole troop) go through the same request.

## 14. Side-view battle

- **Layout.** Actor homes are `(600 + index × 32, 280 + index × 48)` (`Sprite_Actor.setActorHome`, rmmz_sprites.js:739). They enter from
  300 px to the right over 30 frames, step forward 48 px over 12 frames while inputting or acting, step back, and retreat 300 px on escape
  (:735, :883-903). Enemies use img/sv_enemies in side view (`Sprite_Enemy.loadBitmap`, :981).
- **Sheets.** An sv_actors sheet is 9 × 6 cells. Motion `m` is column `(m / 6) × 3 + pattern`, row `m % 6` (`updateFrame`, :808), and the 18 motions
  are listed in `Sprite_Actor.MOTIONS` (:653). Patterns advance every 12 frames; looping motions cycle 0-1-2-1, the rest play once and
  refresh (`updateMotionCount`, :840). Weapons are 96×64 cells, 12 per Weapons*N* sheet, drawn 16 px left of the actor (`Sprite_Weapon`, :2735-2805).
  State overlays are 96×96 cells, 8 frames per row (`Sprite_StateOverlay`, :2663-2730).
- **Which motion.** `refreshMotion` (:857) picks walk (inputting/acting/undecided), dead, sleep, chant (waiting with a magic skill), guard,
  abnormal, dying (HP < ¼) or wait. Attacks use `System.attackMotions[weapon type]` → thrust/swing/missile plus a weapon image
  (`Game_Actor.performAttack`, rmmz_objects.js:4636). Guard, magic skills (`System.magicSkills`), other skills and items use guard/spell/skill/item
  (:4617). Damage and evasion request damage/evade (:4652-4670), and victory and escape request their motions (:4684-4695). A requested motion
  clears a pending refresh (`setupMotion` → `clearMotion`), which is why the victory pose survives the "done" state set at the same time.
- **Action states.** undecided at input start, inputting for the current actor, waiting after input, acting from `performActionStart`, and
  done after the actor's last action (rmmz_managers.js:2564-2582, :2668; rmmz_objects.js:3954).
- **Enemy effects.** whiten 16 frames on action start, blink 20 on damage, collapse 32 (additive, reddish), boss collapse over the bitmap's
  height with Boss Collapse 2 every 20 frames, instant collapse 16, and appear/disappear (`Sprite_Enemy.startEffect`…`updateInstantCollapse`, :1038-1178).

## 15. Parallax

`Game_Map.setupParallax` copies `parallaxName`, `parallaxLoopX/Y` and `parallaxSx/Sy` from the map (rmmz_objects.js:6226). Loops advance
by `sx / tileWidth / 2` tiles per frame (`updateParallax`, :6722). The origin is `parallaxX × 48` for a "!" name (`ImageManager.isZeroParallax`,
rmmz_managers.js:970), `parallaxX × 48 / 2` when looping, and 0 otherwise (`parallaxOx`/`parallaxOy`, :6266-6284). `parallaxX` follows the map's
display position plus the auto-scroll (`setDisplayPos`, `scrollDown`…`scrollUp`, :6247, :6486-6550). Change Parallax (`command284`, :10837) turns off a
loop by resetting that axis (`changeParallax`, :6744). The image is a `TilingSprite` behind the tilemap (`Spriteset_Map.createParallax`,
rmmz_sprites.js:3401).

## 16. Browser deployment

MZ's web runtime is PixiJS plus `effekseer.min.js`/`effekseer.wasm`, loaded by main.js (main.js:5-19, :136). Its `rmmz_*.js` files carry no licence
header that would let another tool redistribute them, so Lakon's HTML export ships its own port of LakonCore instead (web/*.js). Effekseer for
WebGL is MIT-licensed (the header of effekseer.min.js), and Lakon bundles the official 1.70e release from github.com/effekseer/EffekseerForWebGL,
not MZ's copy. MZ games saved in browsers use localforage (`StorageManager.isLocalMode`, rmmz_managers.js:541); the web port uses localStorage.
